## Definition of Done (0.3.x)
- DTU twins exist for at least 2 high-value external systems used by target workflows.
- Scenario harness supports holdout scenarios and emits a satisfaction metric per run set.
- Controlled failure-mode simulation is available and exercised in CI/nightly.
- Provider-aligned codergen backend path demonstrates parity across at least 2 providers with consistent manifest/provenance fields.
- Acceptance tests in this plan are automated and linked from PRs.

## Phase Plan

### Phase A: DTU Foundations
- Owner: Runtime and Platform maintainers
- Goal: define twin contract and execution boundary for deterministic scenario replay.
- Status (2026-02-11): Done.
- Implemented slice artifacts:
  - [`docs/roadmap/0.3-phase-a-dtu-foundations-vertical-slice.md`](./0.3-phase-a-dtu-foundations-vertical-slice.md)
  - [`packages/core/src/dtu/contracts.ts`](../../packages/core/src/dtu/contracts.ts)
  - [`packages/core/src/dtu/runtime.ts`](../../packages/core/src/dtu/runtime.ts)
  - [`packages/core/src/dtu/twins/jira-issue.stub.ts`](../../packages/core/src/dtu/twins/jira-issue.stub.ts)
  - [`packages/core/src/dtu/reference-parity.test.ts`](../../packages/core/src/dtu/reference-parity.test.ts)
- Deliverables:
  - Twin contract schema (requests, responses, error classes, timing model).
  - Initial twin runtime wrapper (in-memory preferred for CI speed).
  - Documentation describing parity expectations and non-goals.
- Exit criteria:
  - Twin contract reviewed and linked from roadmap + solutions docs.
  - At least one reference twin passes parity checks against recorded fixtures.

### Phase B: Scenario Harness and Satisfaction Metric
- Owner: Validation and QA maintainers
- Goal: execute scenario sets at scale with holdout support and scored outcomes.
- Status (2026-02-11): Done.
- Implemented artifacts:
  - [`packages/core/src/dtu/scenario-harness.ts`](../../packages/core/src/dtu/scenario-harness.ts)
  - [`tests/fixtures/dtu/scenarios/`](../../tests/fixtures/dtu/scenarios)
  - [`packages/cli/src/index.ts`](../../packages/cli/src/index.ts) (`dtu-run`)
  - [`docs/roadmap/0.3-dtu-validation-platform-completion.md`](./0.3-dtu-validation-platform-completion.md)
- Deliverables:
  - Scenario runner command and fixture format.
  - Holdout scenario set and scoring rubric (`satisfied` / `unsatisfied` with rationale).
  - Satisfaction report format for trend analysis.
- Exit criteria:
  - Nightly or CI job produces repeatable satisfaction report artifacts.
  - Minimum scenario corpus established (smoke + regression + holdout groups).

### Phase C: Failure-Mode Simulation
- Owner: Reliability maintainers
- Goal: validate resilience behavior under controlled third-party failures.
- Status (2026-02-11): Done.
- Implemented artifacts:
  - [`packages/core/src/dtu/twins/jira-issue.stub.ts`](../../packages/core/src/dtu/twins/jira-issue.stub.ts)
  - [`packages/core/src/dtu/twins/slack-channel.stub.ts`](../../packages/core/src/dtu/twins/slack-channel.stub.ts)
  - [`packages/core/src/dtu/scenario-harness.test.ts`](../../packages/core/src/dtu/scenario-harness.test.ts)
- Deliverables:
  - Failure injection catalog (rate limit, auth failure, malformed payload, timeout, partial outage).
  - Deterministic simulation knobs bound to scenario seeds/config.
  - Retry/failure route coverage across representative workflows.
- Exit criteria:
  - Failure classes are observable in run artifacts.
  - Regression suite includes at least one scenario per failure class.

### Phase D: Provider-Aligned Backend Convergence
- Owner: LLM platform maintainers
- Goal: keep orchestration stable while converging backend behavior across providers.
- Deliverables:
  - Provider profile matrix (tooling/prompt conventions, backend-specific options).
  - Unified telemetry mapping (usage/cost/reasoning/tool events) into run manifests.
  - Cross-provider golden scenarios with normalized expected outputs.
- Exit criteria:
  - Same workflow passes on at least 2 providers with normalized outcome parity.
  - Manifest/provenance fields are consistent and documented.

### Phase E: Governance and Promotion Integration
- Owner: Release and quality maintainers
- Goal: wire DTU confidence into promotion/quality profiles.
- Deliverables:
  - Promotion gate policy linking satisfaction thresholds to `dev/canary/prod`.
  - CI checks that fail promotion when thresholds are not met.
  - Reporting cadence for weekly trend review.
- Exit criteria:
  - Promotion policy documented and enforced in CI.
  - 4-week trend baseline captured in docs.
